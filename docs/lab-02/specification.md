# Lab 2 Sprint Engineering Specification

## 1. Sprint Goal

Deliver the Requester-facing ticketing MVP: a Requester picks a temporary Development
Requester identity, creates a Ticket with supporting attachments, and can find, open, and
manage that Ticket's attachments afterward — all scoped so one Requester can never see
another's data.

## 2. Stakeholder Request Interpretation

IT wants a working intake path before any authentication exists. A Requester must be able
to describe a problem, classify it, attach evidence, and submit it, then later find it again,
search/filter/sort their own list, and manage attachments on it. Because real login is a
Lab 3 concern, a Development Requester selector stands in as the "current user" for testing.
The visual language established here (Zen Green) must be reusable, not screen-specific.

## 3. Scope

### Included
- Development Requester Selection screen and selected-Requester context
- Create Ticket: form, validation, Ticket Number generation, attachment upload
- My Tickets: search, filter (Category, Requested Priority), sort, pagination, ownership scoping
- Requester Ticket Detail: read-only ticket header + attachment management
- Attachment lifecycle: upload, download (active only), soft removal with reason
- Zen Green design tokens and reusable form/list/badge/state components
- Responsive behavior at desktop/tablet/mobile breakpoints

### Excluded
- Authentication, sessions, passwords, real authorization
- IT Staff dashboard, queue, ticket claiming, IT Priority changes
- Public Comments, Internal Notes, Actions Taken
- Any ticket status transition beyond the initial `NEW` status
- Administrator management of users/roles/reference data

## 4. Functional Requirements

- **FR-01** Provide a Development Requester Selection screen listing active Requesters; selecting one establishes the testing context.
- **FR-02** Provide a Create Ticket screen capturing Category, Related System, Requested Priority, Summary, Description, and optional Attachments; creates one Ticket owned by the selected Requester.
- **FR-03** Generate and return a unique Ticket Number for every successfully created Ticket.
- **FR-04** Provide a My Tickets screen listing only the selected Requester's own Tickets.
- **FR-05** Support searching My Tickets by Ticket Number or Summary.
- **FR-06** Support filtering My Tickets by Category and Requested Priority.
- **FR-07** Support sorting My Tickets by Created Date, Ticket Number, Requested Priority, and Current Status.
- **FR-08** Paginate My Tickets and expose pagination metadata (page, pageSize, totalItems, totalPages).
- **FR-09** Provide a Requester Ticket Detail screen showing one owned Ticket's information as read-only.
- **FR-10** Allow the Requester to add a permitted Attachment to an existing owned Ticket.
- **FR-11** Allow the Requester to download an active (non-removed) Attachment they own.
- **FR-12** Allow the Requester to soft-remove one of their own permitted Attachments with a required reason.
- **FR-13** Prevent any Requester from viewing, listing, modifying, or downloading Tickets or Attachments owned by a different Requester.
- **FR-14** Expose active Categories, active Related Systems, and active Requesters as reference data.

## 5. Business Rules

| ID | Rule |
| --- | --- |
| BR-01 | The official Ticket Number is generated by the backend and must be unique (format `TKT-{creation year}-{6-digit zero-padded internal id}`; uniqueness follows from the id's uniqueness). |
| BR-02 | A new Ticket always begins with `currentStatus = NEW`; the client cannot set status at creation. |
| BR-03 | The Development Requester selector stands in for login. Selecting a Requester establishes the testing identity for the browser session only; it is not authentication and grants no real security guarantee. |
| BR-04 | Only Requesters with `isActive = true` are returned by `GET /api/requesters` and selectable in the Selector screen. |
| BR-05 | Selecting a Requester replaces any previously selected Requester. Switching Requesters immediately reloads all Requester-scoped data; any in-progress Create Ticket draft is discarded. |
| BR-06 | Every Ticket belongs to exactly one Requester, set at creation from the currently selected Requester and immutable afterward. |
| BR-07 | Ownership checks for Tickets and Attachments happen server-side on every request; the client only asserts which `requesterId` it is acting as. |
| BR-08 | A request for a Ticket, or an Attachment on a Ticket, not owned by the asserted Requester returns `404 Not Found` — existence is never revealed to a non-owner. |
| BR-09 | My Tickets search matches Ticket Number or Summary (case-insensitive, partial match) against the selected Requester's own Tickets only. |
| BR-10 | My Tickets supports filtering by Category and Requested Priority, independently and combined with search. |
| BR-11 | My Tickets supports sorting by Created Date, Ticket Number, Requested Priority, or Current Status, ascending or descending. Default sort is Created Date descending, with id descending as a stable secondary key. |
| BR-12 | My Tickets paginates results. Default page size is 10, maximum permitted page size is 50. An invalid or out-of-range `page`/`pageSize` is clamped to the nearest valid value rather than rejected. |
| BR-13 | Ticket Summary is required, trimmed of leading/trailing whitespace, and must be 5–120 characters after trimming. |
| BR-14 | Ticket Description is required, trimmed, and must be 10–2000 characters after trimming. |
| BR-15 | Category, Related System, and Requested Priority are required selections from the active reference lists; an unrecognized id is rejected with a validation error. |
| BR-16 | All Create Ticket validation is enforced on both frontend (immediate feedback) and backend (source of truth); the backend never trusts frontend validation alone. |
| BR-17 | The Create Ticket submit control disables the instant a submission begins and stays disabled until the request settles, preventing duplicate Tickets from repeated clicks. |
| BR-18 | If ticket creation fails for any reason, no Ticket is persisted, the form's entered values are preserved on screen, and a safe error message is shown. |
| BR-19 | Allowed attachment types are JPG/JPEG, PNG, WEBP, and PDF only, verified server-side by declared MIME type, not filename extension alone. |
| BR-20 | An attachment upload larger than 5 MB is rejected before being written to storage. |
| BR-21 | A Ticket may not exceed 5 active (non-removed) Attachments; a 6th upload attempt is rejected until an existing Attachment is removed. |
| BR-22 | If a Ticket is created but a subsequent attachment upload fails, the Ticket remains saved and valid; the failed file is reported to the Requester, who may retry the upload from Ticket Detail. No automatic rollback of the Ticket occurs. |
| BR-23 | Attachment removal is a soft removal: the row is retained with `isRemoved = true`, `removedAt`, and `removedReason`; the underlying file is not deleted from storage in Lab 2. |
| BR-24 | A removed Attachment remains visible in the Ticket's attachment list as read-only metadata but cannot be downloaded or previewed. |
| BR-25 | Only the owning Requester may remove one of their own Ticket's Attachments; removal requires a non-empty reason of at least 3 characters. |
| BR-26 | Downloading a removed Attachment returns `404 Not Found`, identical to requesting an Attachment that never existed. |
| BR-27 | If `GET /api/requesters` returns zero active Requesters, the Selector screen shows a safe empty state and blocks entry to the rest of the application. |
| BR-28 | My Tickets distinguishes two zero-result states: the **Empty** state (Requester owns zero Tickets, no filters applied) and the **No-Results** state (a search/filter combination matches nothing, even though the Requester owns Tickets elsewhere). Copy and available actions differ between the two. |
| BR-29 | The Development Requester selector, its client-stored selection, and every ownership check built on `requesterId` are temporary Lab 2 scaffolding. Lab 3 replaces the asserted `requesterId` with the authenticated session's user id; no Lab 2 code may treat the selector as a secure identity source. |

## 6. UI Specification Summary

See `docs/lab-02/ui-spec.md` for the full Zen Green token set, component states, and the four
required screens (Development Requester Selection, Create Ticket, My Tickets, Requester Ticket
Detail). Summary: primary green `#006B3C` app shell / primary actions; consistent field states
(editable, read-only, invalid, disabled, focused); required-field asterisks paired with adjacent

992px / 768px with no horizontal scroll at any size.

## 7. Data Changes

New Prisma models (see `server/prisma/schema.prisma` once implemented):

- **Requester** — `id`, `name`, `email` (unique), `isActive` (default `true`), `createdAt`.
- **RelatedSystem** — `id`, `name` (unique), `createdAt`.
- **Ticket** — `id`, `ticketNumber` (unique), `requesterId` (FK → Requester), `categoryId` (FK → Category), `relatedSystemId` (FK → RelatedSystem), `summary`, `description`, `requestedPriority` (enum `LOW`/`MEDIUM`/`HIGH`), `currentStatus` (enum, only `NEW` reachable in Lab 2), `createdAt`, `updatedAt`.
- **Attachment** — `id`, `ticketId` (FK → Ticket), `originalFilename`, `storedFilename` (unique, e.g. UUID + extension), `mimeType`, `sizeBytes`, `isRemoved` (default `false`), `removedAt`, `removedReason`, `createdAt`.

`Category` (from Lab 1) is reused unchanged.

Relationships: one Requester → many Tickets; one Ticket → one Requester; one Ticket → many
Attachments; one Category → many Tickets; one RelatedSystem → many Tickets.

Indexes: `Requester.email` unique; `RelatedSystem.name` unique; `Ticket.ticketNumber` unique;
`Ticket.requesterId` indexed (every ownership-scoped query filters on it); `Attachment.ticketId`
indexed (attachment list is always fetched per ticket).

**IT Priority and Ticket Owner (assigned IT Staff) are intentionally not modeled in Lab 2** — they
belong to the IT Staff workflow explicitly excluded from this sprint (§4.2 of the handout) and are
deferred to the lab that introduces IT Staff functionality.

## 9. Acceptance Criteria

| ID | Criterion |
| --- | --- |
| AC-01 | Given valid Ticket data, when the Requester submits the form, then one Ticket is saved and the official Ticket Number is displayed. |
| AC-02 | Given no Development Requester is selected, when the user attempts to open My Tickets, then the Requester Selection screen is shown. |
| AC-03 | Given Requester B is selected, when a Ticket belonging to Requester A is requested, then the Ticket data is not returned. |
| AC-04 | Given Category, Related System, or Requested Priority is left unselected, when the Requester submits Create Ticket, then a field-level message appears under each missing field and no API call is made. |
| AC-05 | Given a Ticket Summary shorter than 5 characters, when submitted, then a validation message states the minimum length and the Ticket is not created. |
| AC-06 | Given a valid submission is in flight, when the request is pending, then the Submit button shows a busy state and is disabled until the response arrives. |
| AC-07 | Given the backend is unreachable during Create Ticket submission, when the Requester submits a valid form, then a safe error message is shown and all entered field values remain in the form. |
| AC-08 | Given a file larger than 5 MB is selected as an attachment, when the Requester attempts to add it, then the file is rejected inline and is not uploaded. |
| AC-09 | Given a file of an unsupported type is selected, when the Requester attempts to add it, then the file is rejected inline, naming the allowed types. |
| AC-10 | Given a Ticket already has 5 active Attachments, when the Requester attempts to add a 6th, then the upload is rejected with a message explaining the limit. |
| AC-11 | Given Requester A has 2 Tickets and Requester B has 3, when Requester A opens My Tickets, then only Requester A's 2 Tickets are listed. |
| AC-12 | Given the selected Requester is switched from A to B, when the switch completes, then My Tickets reloads and shows only B's Tickets. |
| AC-13 | Given a search term matching no Ticket Number or Summary, when the search runs, then the No-Results state is shown with a Clear Filters action. |
| AC-14 | Given the selected Requester owns zero Tickets, when My Tickets loads with no filters applied, then the Empty state is shown, distinct from the No-Results state. |
| AC-15 | Given more Tickets exist than one page size, when the Requester opens page 2, then a different, non-overlapping set of that Requester's Tickets is shown. |
| AC-16 | Given a sort by Requested Priority descending, when the list renders, then Tickets appear High → Medium → Low, with Created Date descending as the tie-break. |
| AC-17 | Given a Ticket owned by the selected Requester, when its Ticket Detail opens, then all header fields render as read-only. |
| AC-18 | Given a Ticket Detail with 3 active Attachments, when a valid 4th is added, then it appears immediately without a full page reload. |
| AC-19 | Given an active Attachment on an owned Ticket, when the Requester clicks Download, then the original file downloads successfully. |
| AC-20 | Given the Requester removes an Attachment with a reason, when removal completes, then the Attachment stays listed with a "Removed" indicator and reason, and Download is no longer available. |
| AC-21 | Given an Attachment has been soft-removed, when any client requests its download URL directly, then the server returns 404. |
| AC-22 | Given the Requester attempts removal without a reason, when they submit, then a validation message blocks the removal and nothing changes. |
| AC-23 | Given no active Development Requesters exist, when the Selector screen loads, then a safe empty state is shown and nothing is selectable. |
| AC-24 | Given the Requester API call fails on Selector load, then a safe failure state with a retry option is shown. |
| AC-25 | Given a mobile viewport (<768px), when Create Ticket, My Tickets, or Ticket Detail render, then no control is clipped and the page does not scroll horizontally. |
| AC-26 | Given a keyboard-only user tabs through Create Ticket, then a visible focus indicator appears on every interactive control, including the Requester dropdown. |

## 11. Assumptions and Decisions

- **"Active" Categories/Related Systems**: unlike Requesters, the handout never describes deactivating a Category or Related System. Lab 2 does not add an `isActive` column to either — all seeded rows are returned by their `GET` endpoints. Documented here per §5.2's requirement to justify at least one design decision.
- **`requesterId` transport**: since there is no session, every Ticket/Attachment-scoped request carries `requesterId` explicitly (body field on writes, query param on reads) rather than a header, matching the handout's partial example JSON. This is deliberately visible, temporary scaffolding per BR-03/BR-29, not a security boundary.
- **Ticket lookup key**: `GET /api/tickets/:id` uses the internal numeric `id`, not the display `ticketNumber` — simpler indexing/routing; `ticketNumber` remains the user-facing identifier and a searchable field.
- **File storage**: attachments are stored on local disk under the server (e.g. `server/uploads/tickets/{ticketId}/{uuid}.{ext}`) with the original filename retained only as metadata. Object storage is out of scope for Lab 2.
- **Zen Green vs. Bootstrap**: `client` already depends on Bootstrap (from Lab 1) but the current UI doesn't use it. Lab 2 introduces dedicated Zen Green CSS custom-property tokens and component classes rather than Bootstrap's default theme, since Bootstrap's defaults don't match the required palette; Bootstrap's grid utilities may still be used where convenient.
- **New dependencies required**: `react-router-dom` (client has zero routing today) and a multipart upload middleware such as `multer` (server has none). Both are added in their respective foundational Issues, not silently assumed.
- **Duplicate-submission prevention** is client-side only (disable-on-submit, BR-17); no server-side idempotency key is implemented in Lab 2.
